# 2026-10-23 并发修复与复测

> 后续已为点赞/评论补充持久消息、确认发布、去重与有限重试，并修复消息领取的范围锁竞争。最新结果见 [消息可靠性处理与验证](P0-MESSAGE-RELIABILITY-20261023.md)。下文保留此前快照的性能与 Windows 入口诊断，不能直接作为新版本容量结论。

当前结论：持续读取的严重失败在渐增负载下未复现；热点写入的新排队机制通过两轮 300 并发验证。补充对照显示，同一 Linux API 经 Docker 内部网络突发连接 1,500/1,500 成功，经 Windows 映射入口则有 67/1,500 次连接拒绝。剩余问题更指向本机网络入口，具体机制仍未关闭。

## 修改与原因

沿用当前工作区已有的 MySQL/Redis 连接池、Feed 批量查询及 singleflight、互动事务与幂等、通知查询错误传播等修改。API 与 Worker 每进程 MySQL 连接上限为 64，profiling 端口可读取 `/debug/dbstats`。

本轮完整压测发现：300 并发同时写同一视频时，大量事务等待视频行锁，占用共享数据库连接，鉴权也受到影响。完整复测的 300 并发点赞失败 10/2,000 次（7 个鉴权 503、3 个客户端超时），评论超时 8/2,000 次。连接池有上限仍不足以隔离热点写入。

新增 `backend/internal/video/write_gate.go`：点赞、取消点赞和发布评论在借用 SQL 连接之前，按视频 ID 排队；同视频最多 4 个请求进入写入流程，不同视频独立。等待遵循请求 Context，空闲条目自动清除。数据库事务及唯一索引仍承担跨实例的一致性保证，本地队列不能协调多实例总并发。

严格串行曾使吞吐下降、出现更多 3 秒超时，已弃用；该失败实验完整保留。最终保留并行度 4，验证成功率及数据核对后才记录为当前实现。

补充真实 MySQL 通知回归：作者查询失败时必须 NACK 重排队；恢复后重试产生正确通知再 ACK。补充排队并发上限、不同视频互不阻塞、取消等待及条目清理测试。中文汇总脚本移除历史基线的硬编码结论，增加连接池采样。

## 验证与限制

- 设置隔离 MySQL DSN 后，`go test ./...` 通过，包含真实 MySQL 连接池和通知故障恢复测试。
- `go vet ./cmd/... ./internal/video ./internal/worker ./internal/db ./internal/observability` 通过。
- `git diff --check` 通过。每轮目录保留二进制 SHA256、已跟踪文件补丁、版本、资源及原始 JSON；工作区有其他同时进行的修改，应按具体快照解释结果。
- Windows `go test -race ./internal/video ./internal/worker -count=1` 的两个测试进程均以 `0xc0000139` 退出，未完成竞态检测；不能声称 race 检查通过。
- 单视频写吞吐仍受同一数据库行更新限制，本次并非长期持续写入测量。提高连接数不能提高该行的串行处理能力。
- 数据库提交与 MQ 发布之间仍没有事务 Outbox；本次无故障写入核对通过，不证明 MQ 故障时事件绝不丢失，也不证明消费者任意重投时副作用幂等。

## 未关闭：冷启动连接拒绝

API 进程存活，建立连接并进入稳定状态后读取正常，但首次同时新建 300 个连接仍可失败。不能再声称所有连接拒绝已经消失。

本机 Go 运行时 Windows 监听使用 `SOMAXCONN`。Microsoft 文档说明，Windows 的实际监听队列受服务提供程序控制，队列满可能返回 `WSAECONNREFUSED`；因此监听队列及 Accept 调度是候选原因，尚未通过抓包或独立对照确认。该文档也说明，对已经监听的 socket 再调用 listen 不会修改 backlog，不应加入无效的“再次 listen 扩容”代码。[Microsoft listen 文档](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-listen)

只读检查未读到最近两小时 4227/4231 端口耗尽事件，IPv4 动态 TCP 端口范围为 1024 起、64,511 个端口；这些检查不能单独排除所有网络原因。Linux API 对照也经 Windows 端口映射出现首轮连接拒绝，因此不能将问题仅归因于原生 Windows API 的 Go 监听队列。

## Linux 对照与网络入口探针

`results/20261023-014801` 为第一轮 Linux API/Worker 对照。API/Worker 默认 UTC，Windows 夹具与 MySQL DSN 的 Local 时区为 UTC+8；冷数据和分页校验因此失真，该轮读取结论无效。首次突发读取仍记录 286 次 API 连接拒绝。该轮两组点赞、两组评论各 2,000/2,000 成功、最终核对通过，只用作补充证据，不据此宣布 Linux 整体通过。

`results/20261023-015146` 显式将测试容器时区对齐为 Asia/Shanghai，并只读复测。首轮登录 Feed 205,685/206,438 成功，753 次连接拒绝；第二轮 203,473/203,473 成功。两轮冷数据 Feed 分别 243,782/243,782、243,774/243,774 成功，有效 RPS 约 12,169/12,174。分页前后均通过。两次服务端使用相同应用源码的 Linux 静态构建，压测器仍在 Windows；数据库网络路径也变为容器内部，因此不能把吞吐差异仅归因于操作系统。

随后用同一个只读探针源码分别编译 Windows/Linux 版本，访问同一 Linux API。每轮新建 HTTP Transport，300 个客户端同时发起一次匿名 Feed 请求，进行 5 轮；检查 HTTP 200 和 10 条视频响应。Docker 内部通过服务 DNS 直接访问，Windows 通过已发布的 `127.0.0.1:18088` 访问：

| 发起端/入口 | 有效响应 | 连接拒绝 |
|---|---:|---:|
| Linux 探针 → Docker 内部 API | 1,500/1,500 | 0 |
| Windows 探针 → 本机映射端口 | 1,433/1,500 | 67 |

原始分轮结果为 `results/20261023-015146/connection-probe-linux.jsonl`、`connection-probe-windows.jsonl`。源码为 `test/load/connection-probe/main.go`。探针没有登录鉴权、持续负载或写入，不能替代业务容量测试；但该对照使剩余连接拒绝更指向 Windows 客户端/本机网络/转发入口，而不是热数据 SQL 或该 Linux API 的业务实现。探针按 Linux → Windows 顺序执行，不构成严格随机对照，也尚未定位 TCP 的具体拒绝点。

建议后续容量压测将压测器与服务都放在 Linux 网络环境中，同时保留 Windows 入口突发连接测试作为独立环境问题。若继续修复本机入口，应抓取两条路径的 SYN/RST 与 Accept 时序；不要隐藏首轮失败、放宽客户端超时，或把 Windows 入口的连接拒绝直接当成数据库并发容量。
